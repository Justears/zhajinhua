# 后周炸炸炸 · DS923+ 好友联机版

为群晖 DS923+（AMD64）准备的 2–8 人网页炸金花。使用 Container Manager，一个容器即可运行，无需数据库、npm 安装或大模型 API。

## 推荐安装：离线镜像 + Container Manager 项目

1. 从本仓库 Releases 下载离线安装包，在电脑解压整个 ZIP，得到 **jinhua** 文件夹。将整个文件夹上传到群晖的 **docker** 共享文件夹，即 **/volume1/docker/jinhua**。如果你使用别的存储卷，选择对应目录即可。
2. 打开 **Container Manager → 映像 → 新增 → 从文件新增**（部分版本显示为“导入”），选择文件夹里的 **jinhua-amd64.tar**。完成后应出现 **jinhua-friends:1.2.2**。
3. 先将 `.env.example` 复制为 `.env`，在里面填写你自己的入场密码（至少 8 位）；然后打开 **Container Manager → 项目 → 新增**。名称填写 **jinhua**；路径选择刚才的 **docker/jinhua**；来源选择该目录已有的 **docker-compose.yml**。如果界面要求上传 YAML，就上传同名文件。
4. 按向导创建并启动项目。无需设置 Web Station 门户。等待容器显示“正在运行”，健康检查约 30 秒后显示正常。
5. 手机/电脑连接同一局域网，在浏览器打开 `http://你的群晖IP:18780`。例如群晖 IP 是 192.168.1.50，就打开 `http://192.168.1.50:18780`。
6. 输入你在 `.env` 中设置的入场密码。填写昵称，创建牌桌，把右上角邀请链接和入场密码告诉朋友。朋友入座后，由房主点击“开始发牌”。

公开发行版不预置通用密码。请在 `.env` 中设置 ROOM_PASSWORD，至少 8 位；不要将 `.env` 上传到 GitHub。更改后需重新部署项目配置。

## 为什么推荐容器，不做 SPK

容器能把 Node 运行时与应用一起导入，安装、删除、升级和回滚更直接。SPK 需要另外适配 DSM 版本、安装脚本及服务用户权限；本项目维护 Docker 版。

## 已整合的功能

- 多房间，每桌 2–8 人，2/4/6/8 人桌可选；候场可增减座位。
- 闷牌、看牌、跟注、加注、比牌、弃牌、下一局。
- 60 秒默认限时，可选 30/90/120 秒，超时自动弃牌，看牌不延时。
- 房主才可发牌、开下一局、调整座位和关闭房间。
- 隐藏手牌由服务端控制，未看牌时也不会发到自己的浏览器。
- 邀请链接、6 位房间码、中文聊天、当场积分和最近 50 局结果。
- 同一浏览器刷新/断线后续局；进程重启保存房间、积分和手牌，并重新给当前玩家完整操作时间。
- 页面和素材全部本地提供，不依赖外部 CDN。

## 本桌的规则差异

牌型：豹子 > 同花顺 > 同花 > 顺子 > 对子 > 散牌。A23 为最小顺，不比花色。杂色 235 克豹子可以开关；多人摊牌遇到循环克制时按普通牌型结算。

本局开头每人交底注，闷牌跟注为“当前注”的一半，看牌后全价。当前注明牌价最大为初始底注的 10 倍；闷牌实际加注最多为其一半。所有未弃牌、未全押玩家完成首轮行动后才能比牌。比牌支付一次当前注，同牌时发起方输。

**沿用 Bisca 的简化全押规则：筹码不足可全押，仍参与整个底池结算，不设边池。** 这是本版确定的娱乐规则，并非所有地区通用规则。

每局积分带入下一局。不够底注的玩家轮空；只剩一个人够底注时整场结束。房主“返回候场”后可以调整座位，重新开始会重置所有人的积分。游戏中途新人不能插入，须等待返回候场。

## 数据与备份

唯一的持久化目录是 **jinhua/data**。包含 config.json（座位认证密钥）及 room-XXXXXX.json（房间存档）。不要通过 Web Station 公开这个目录。

备份：先停止项目，复制整个 data 文件夹，再启动项目。恢复：停止项目，放回备份的 data，再启动。保留 config.json 才能让原浏览器继续认回自己的座位。

仅刷新或关闭页面不会离座；同一浏览器下次进入可续局。清除网站 Cookie、无痕窗口或换设备会被识别为另一位玩家；需要房主在候场时移除旧座位。会话有效期 90 天。

## 端口、权限与网络

- 默认群晖端口 **18780**，容器内端口 **8080**。在 `.env` 中设置 `GAME_PORT` 可以调整群晖这一侧的端口。升级时保留原端口。
- 容器不是特权模式，不挂载 Docker 套接字，也不使用 host 网络。仅 data 目录可写。
- 如果启用了 DSM 防火墙，允许可信局域网访问 TCP 18780。
- 外网朋友无法使用局域网 IP。需具备可用的直连或 VPN 路线，公网网页入口建议配置 HTTPS。反向代理不会自动打通网络；仅有 IPv6 地址时，直连的朋友也需要可用 IPv6。QuickConnect 不会自动转发此应用。
- 反向代理建议独立域名映射到 HTTP 127.0.0.1:18780，并保留 Host 请求头；本应用部署在域名根路径，不支持 /jinhua 这样的子路径。
- 使用 SSE 实时推送，代理应关闭响应缓冲，并允许长连接。即使 SSE 暂时断开，页面也有轮询恢复。
- 全站通过 HTTPS 使用时，可把 COOKIE_SECURE 改为“true”；纯 HTTP 局域网保持“false”。

## 使用群晖自带 HTTPS 反向代理

v1.2.0 新增独立配置 **docker-compose.proxy.yml**，适合已有 DSM 反向代理的用户。它将后端端口绑定到 `127.0.0.1`，并启用 Secure Cookie。具体步骤、IPv6 防火墙检查和适用限制见 [安全部署说明](SECURITY.md)。

这个 YAML 应单独使用，不要与默认 YAML 叠加运行，否则 Compose 合并端口时可能保留原来的直接入口。首次局域网测试继续使用默认 `docker-compose.yml`。

更改入场密码并重新创建容器后，旧登录将失效。朋友使用原浏览器输入新密码，可以恢复原来有效凭证对应的座位。不要清除 Cookie 或删除 data/config.json。

## 排错

### 无法找到 jinhua-friends:1.2.2
先完成离线 TAR 的映像导入，再创建项目；映像名称必须一致。不要只上传源代码然后尝试在线搜索这个镜像。

### 容器启动后退出
打开日志。提示 ROOM_PASSWORD 时检查密码至少 8 位；提示 EACCES/权限不足时，检查项目路径和 data 文件夹的读写权限。默认使用容器内部 root 用户写入该挂载目录，无需特权模式。

### 存档报错
本版遇到损坏 JSON 会停止启动，不会悄悄丢弃旧房间。从最近的 data 备份恢复后启动。

### 浏览器打不开
确认 IP 是群晖局域网 IP；确认容器运行正常、18780 未冲突、DSM 防火墙放行。不要直接在浏览器输入“0.0.0.0”。

### 按钮提示牌局变化
其他玩家操作、超时结算或座位变更可能使牌局版本更新。按最新画面重新点击，服务端不会重复扣积分；普通聊天不会使正在选择的合法动作失效。

## 在线备用方案 / 自行构建

正常安装不需要这些步骤。

- 在线备用：将 docker-compose.online.yml 作为项目 YAML。它直接运行随包源码，首次会下载 Node 官方镜像。不能和离线方案同时占用同一个容器名/端口。
- 自行构建：在项目目录执行 docker build -t jinhua-friends:1.2.2 .，然后使用默认 Compose 文件。
- 本地开发：Node.js 22 或更新版本，设置 ROOM_PASSWORD 后执行 npm start。
- 测试：npm test。

维护发布：更新 package.json 中的版本以及 Compose 镜像版本后提交到 main，GitHub Actions 会构建、测试并发布离线包；也可在 Actions 中手动运行发布流程。已公开的同版本 Release 不会被覆盖，失败草稿可重试。测试或容器检查失败时不会公开新版本。ZIP 校验值下载自同一 Release，镜像校验值在 ZIP 内。

## 从旧版升级

1. 先结束正在进行的牌局，再在 Container Manager 停止原来的 jinhua 项目。
2. 备份整个 data 文件夹和你自己的 .env 文件；它们保存房间、积分、座位身份和入场密码。
3. 解压新版离线包，将程序文件覆盖到原目录，保留旧 data 文件夹和 .env，不要用空目录替换存档。
4. 导入新版 jinhua-amd64.tar（jinhua-friends:1.2.2），使用选定的新版 Compose 文件重新创建项目容器。仅重启旧容器不会切换镜像或环境变量。
5. 使用原来的访问地址和浏览器打开。首次从 v1.1.1 升级需要重新输入入场密码，验证成功后可继续原座位。升级后的进行中牌局会重新给予一轮操作时间。

需要回退时：停止项目，恢复升级前备份的 data 和旧版程序、镜像及配置，再启动。
